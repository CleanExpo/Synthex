# Spec: Entity-Scoped AI Chat (CRM pattern → Synthex)

> **Status:** DRAFT for review — no code until approved (Fabel spec-first gate).

> **Linear:** propose a new issue (e.g. SYN-XXX) — referenced in code/commits, not filenames.

## Finish line (one sentence)

A Synthex user can open an AI conversation **scoped to a specific record** (a Campaign, Organization/client, or Post) and the chat automatically carries that record's context, instead of every chat being a generic user-level session.

## Why this is the only clean CRM-pattern fit for Synthex `[INFERENCE]`

The CRM video's portable patterns are: per-record AI enrichment, lead scoring, a per-entity chatbot, transactional email, and background automations. Against the Synthex capability map:

- Transactional email (Resend) — **already exists** (`lib/email-service.ts`, `resend@6.9.1`).
- Background automations — **already exists** (BullMQ + 37 crons).
- Lead scoring / per-record enrichment — **no home in Synthex** (no leads/pipeline domain; these belong in `apps/web`, the actual CRM).
- **Per-entity chatbot — genuine, bounded gap.** Synthex already has user-level chat (`AIConversation`/`AIMessage` + `lib/ai/chat-assistant/`), so scoping it to a record is a small, high-value extension that reuses existing infrastructure.

Everything else from the CRM video is either already present or out of scope for Synthex (recommend `apps/web`).

## Current state `[VERIFIED]` (from repo map)

- `model AIConversation` — `userId`, `title`, `status` (active/archived/deleted), `contextSnapshot` (compressed context for continuity), `messageCount`, `lastMessageAt`. **No entity linkage.**
- `model AIMessage` — `conversationId`, `role`, `content`, `tokenCount`.
- Routes: `POST /api/ai/chat/[conversationId]/send`, `GET /api/ai/chat/[conversationId]`.
- Streaming: `lib/ai/chat-assistant/` (SSE).
- Conventions: multi-tenant `organizationId` scoping on org tables; Zod on all writes; auth via `lib/auth/with-auth.ts` + `with-org.ts`; Prisma migrations via `apply_migration` (never `prisma db push`); new columns must be nullable or have defaults (backward-compatible).

## Design

### Data model (backward-compatible, additive)

Add two **nullable** columns to `AIConversation` (so existing user-level chats are unaffected):

- `entityType` — enum `EntityScope { ORGANIZATION, CAMPAIGN, POST }` (start with these three; extensible). Nullable.
- `entityId` — `String?` (cuid of the scoped record). Nullable.

Index `(organizationId, entityType, entityId)` for "list chats for this record".

Migration: additive, nullable, no backfill — satisfies Synthex's no-breaking-migration rule. Applied via `apply_migration`.

### Context injection

When a conversation has `entityType`/`entityId`, before the LLM call:

1. Load the referenced record **org-scoped** (`where: { id: entityId, organizationId }`) — never cross-org.
2. Build a compact `contextSnapshot` from the record (e.g. Campaign: name, goal, status, post count, date range; Organization: name, brand DNA summary; Post: platform, status, body excerpt).
3. Prepend that snapshot to the existing chat-assistant system prompt. Reuse the existing `contextSnapshot` field rather than inventing a parallel mechanism.

If the record is missing or not in the caller's org → 404 (don't leak existence), consistent with Synthex's 401→403→404→200 route discipline.

### API surface (reuse, don't replace)

- Extend conversation creation to accept optional `{ entityType, entityId }` (Zod-validated; both-or-neither). Validate the record exists + is in-org at creation.
- Add `GET /api/ai/chat?entityType=CAMPAIGN&entityId=...` → list conversations for a record (org-scoped).
- `send`/streaming paths unchanged except for the context-injection step.

## Out of scope (YAGNI)

- Multi-user / shared entity chats.
- Incremental/continuous learning of the snapshot mid-conversation (snapshot is built per turn from live data — good enough).
- Lead scoring, per-record enrichment, new CRM entities — recommend `apps/web`.
- UI work beyond what's needed to pass an entity scope to the existing chat component (separate task once API lands).

## Prerequisites / gated items

- None external. No new dependencies (uses existing Prisma/Supabase/chat-assistant). Satisfies `dependency-discipline`.
- One Prisma migration (additive) applied via `apply_migration` against the Synthex Supabase project — **gated**: prod schema change requires founder approval per Synthex DB rules.

## Verification (definition of done)

- Migration applies cleanly; existing user-level chats keep working (entityType/entityId null).
- Creating an entity-scoped chat with a cross-org `entityId` returns 403/404 (test required — 401→403→404→200 order per `api-testing`).
- An entity-scoped chat's first LLM call includes the record's context snapshot (assert the system prompt contains the injected fields).
- `GET` by entity returns only that org's conversations for that record.
