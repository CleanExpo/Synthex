# Synthex Social Pipeline — v0

Seven prompts, restructured as a pipeline. Each node has a bounded job, an input it reads
explicitly, and an output shape the next node consumes without a human in between.

Companion to `synthex-prompt-library.md` (image and motion archetypes). This file covers
strategy and copy.

## Why not a prompt pack

The original set is a chain wearing seven hats. Strategy produces the positioning that
pillars need; pillars produce the themes the calendar needs; the calendar produces the
slots that post copy needs. Stored as seven independent prompts, every one re-asks for
context the previous step already generated, and the user pastes their business
description seven times.

Three changes were made:

- **Grounding moved to a stored object.** `BRAND_CONTEXT` is written once per client and
  read by every node. No node asks the user to describe the business.
- **Output contracts added.** Free text between nodes means a human parses every handoff.
- **Role-play preambles removed.** "Act as a top-tier community manager who handles
  accounts for major brands" narrows the exploration space without adding capability.
  Describe the job and the constraints; the model does not need a costume.

Hooks and captions delegate to the estate copywriting standard rather than being
reimplemented here.

## Stage two organic campaign preparation

The campaign unit is a useful lesson followed by a relevant, optional next step:

```
CAMPAIGN_BRIEF {
  campaign_id:       string        // stable identifier, never inferred from copy
  audience:          string
  channel:           string        // channel context changes the format and ask
  problem:           string        // the audience's stated problem
  solution:          string        // useful education that stands alone
  usable_tool:       string        // checklist, lesson, calculator or other asset
  optional_next_step: string       // relevant offer; never implied entitlement
  proof_sources:     string[]      // source URLs or owned records
  hypothesis:        string
  success_measure:   string
}
```

Preparation must produce a preview pack, not a publish action. The first two campaign
packs remain subject to Phill's review. No customer message, automatic billing, paid
promotion or provider connection is implied by this brief.

### Measurement acceptance

Before a campaign is eligible for review, its preview must demonstrate this trace with
fixtures or an approved manual check:

1. Every destination link is generated by `lib/utm/build-utm-url.ts` with a stable
   `utm_campaign` equal to `campaign_id`, plus source, channel medium and content
   variant. Hand-built UTM strings are rejected.
2. The landing page and usable tool identify the same campaign and can record visits,
   tool uptake and lesson completion where that surface supports completion events.
3. A qualifying enquiry, booking and attributed revenue can be joined back to the
   campaign through the existing event/session/UTM path. Missing joins are recorded as
   `unknown`, never converted into a positive attribution.
4. The pack names the data source and access mode for each measure (`owned_analytics`,
   `official_api`, `manual_review` or `blocked`), the observation window and the sample
   limitation. Likes alone do not satisfy acceptance.
5. The campaign records one hypothesis, one outcome decision (`expand`, `improve` or
   `stop`) and one justified next change. The performance-review node remains disabled
   until real analytics are wired to published post records.

The existing UTM builder, engagement-event schema and attribution engine are the
implementation surfaces to reuse. This section defines the preparation and acceptance
boundary; it does not claim that the full live trace or analytics connector exists.

### Existing-product boundary

`usable_tool` must reference an existing, owner-approved asset. The campaign pipeline
does not create a generic calculator, checklist app, CRM, checkout, training product or
customer database to fill a copy brief.

| Existing surface | Campaign role                                                                      | Current evidence boundary                                                                                                                     |
| ---------------- | ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| RestoreAssist    | Existing trial, onboarding, inspections, AI reports, integrations and upgrade path | The current repository help content states a 15-day trial; live commercial terms still need a live check before promotion.                    |
| CARSI            | Formal courses, lessons and learner progress                                       | CARSI remains the training owner; a RestoreAssist subscription does not imply paid CARSI entitlement.                                         |
| Synthex          | Organic content preparation, tagged links, event capture and attribution reporting | UTM, event and attribution code exists; the performance-review node remains disabled until real analytics are connected to published records. |
| CCW              | Existing equipment, supplies, inventory, servicing and service-request surfaces    | Use only verified owner-approved routes and records; no cross-product customer relationship is assumed.                                       |

The smallest legitimate gap is a preparation adapter: map a campaign brief to one
existing landing/onboarding/training asset, generate its canonical tagged links, and
provide the measurement acceptance record. This is a bounded internal change with no
new service, package, spend or data-sharing path. If an existing asset cannot satisfy
the requested action, the campaign stays in draft and records the missing capability
instead of inventing a replacement.

### Stage three cadence and activation loop (draft only)

Stage 3 should connect editorial, training, activation and learning into one small
experiment. The public message stays consistent—problem, useful solution, proof and an
optional next step—but each channel earns its own format. Repetition can build familiarity;
it cannot establish truth, so claims remain tied to `proof_sources` and never include
unsupported competitor allegations.

The audience-moment hypothesis is deliberately testable, not a claim that a release is
automatically authorized. The current operating target is **4:00pm Australia/Brisbane every
day**. This is a release-review target and preparation deadline; it does not bypass approval,
receipt, rights, quota or zero-spend gates. Review attendance is flexible.

- a start-of-day practical action may help a prospect apply one useful idea and enter an
  existing RestoreAssist trial, CARSI lesson, community route or other approved surface;
- an end-of-day digest may help them return to the same researched topic, complete the next
  lesson selected from an actual blocker, or take the optional qualified next step; and
- one researched topic can be adapted across a short explanation, existing-tool walkthrough,
  lesson prompt and digest, with the source and campaign identity retained at every handoff.

The smallest reviewable candidate is a two-touch campaign pack, not a new product:

1. Select one evidenced topic and one existing destination. Record the audience problem,
   proof sources, useful action, relevant existing CRM/trial/CARSI/community route, blocker
   that would select the next lesson, and one success measure.
2. Prepare one practical-action variant and one digest variant with the same stable
   `campaign_id`, canonical UTM links, explicit destination and timezone-aware proposed slot.
   The 4:00pm Brisbane target is now the operating target; other times remain hypotheses and
   must not be inferred from it.
3. Keep a small reserve queue containing only approved, unsent posts. Dedupe on
   `campaign_id + channel + slot + content_variant`; a repeated message must add a distinct
   useful action or evidence, not just restate the claim.
4. Require Phill's review for the first two campaign packs. No customer message, automatic
   billing, paid promotion, provider connection or recurring automation is authorized by
   this brief. The personal calendar marker is a transparent reminder only; it does not
   activate the publishing pipeline or prove Mission Control sync.
5. Use the existing Synthex calendar/scheduler and publish path: `hooks/useCalendar.ts`,
   `lib/calendar/*`, `lib/marketing-agency/publish-gate.ts`,
   `lib/marketing-agency/publishing-handoff.ts`, `lib/publish/publishQueue.ts`, and
   `app/api/cron/publish-scheduled/route.ts`. These are reuse points, not a second system.
6. A post becomes live only when the platform receipt, URL or API response is stored. Use a
   bounded retry count and an idempotency key derived from the dedupe key; exhausted retries
   stay failed and alert with the intended IANA timezone, local slot, channel, campaign ID
   and reason. A missed slot is not silently moved to an unapproved time.
7. Learn from repeat useful actions, trial value and downstream outcomes—not likes alone:
   visits, useful-tool uptake, lesson completion where supported, qualified enquiries,
   bookings, attributed revenue, unknown attribution, time window, sample size and included
   usage. Later analytics may change cadence, format or the next lesson, but cannot turn
   repetition into evidence.

Acceptance for this candidate is: timezone-explicit slots; a capped approved reserve queue;
source-backed claims; no duplicate key; human approval; bounded retry; receipt-required live
status; missed-slot alerting; and explicit `unknown`/small-sample states. The minimum genuine
implementation gap is limited to mapping these fields to existing campaign/calendar records,
preserving the handoff receipt and alerting on failure. Do not build a standalone calculator,
CRM, content library, lesson system or analytics platform to fill that gap.

### Private owner briefing -> public Margot progress series (mock brief; generation blocked)

This is a proposed two-surface workflow, not permission to generate or publish:

- **Private owner brief:** a daily internal summary of verified completions, current blockers,
  decisions needed, and the next useful action. It may contain private operational detail.
- **Public series:** a separate, public-safe behind-the-scenes progress update presented by
  Margot as an explicitly labelled AI presenter. It may include only approved milestones,
  why the work matters, and the next public-safe step. It must exclude private clients,
  credentials, customer data, unreleased sensitive work, internal blockers and unverifiable
  claims. Phill is not the public presenter for this series.

**Canonical identity gate.** The repository SSOT maps Margot to the canonical asset path
`/margot/avatar.png`, the canonical visual identity record at
`.harness/margot/assets/margot_identity.json`, and the Margot-only ElevenLabs voice constant
`MARGOT_ELEVENLABS_VOICE_ID`. A live HeyGen private-avatar inventory check found Phill
McGurk digital-twin assets and Claire/CARSI/training assets, but no Margot-named avatar or
digital-twin look. Therefore the presenter mapping is `blocked: canonical Margot HeyGen
asset not found`; do not substitute Phill, Claire, a training avatar, or an unnamed stock
avatar. Generation requires a confirmed Margot asset ID, approved script, consent/rights
record, budget and retry caps, and first-two-campaign human review.

**Draft public script shape (not a generated script):**

> Hi, I’m Margot, an AI presenter for Unite-Group. This week we completed **[verified,
> > public-safe milestone]**. It matters because **[plain-language benefit]**. Next we’re
> preparing **[public-safe next step]**. This is a progress update, not a claim that the
> work is finished; we’ll share the next verified result when it is ready.

The production record should retain source evidence, approval state, public/private
classification, presenter asset ID, voice reference, usage-rights reference, cost mode,
generation status, QA result and publication receipt. Current mode is `mock_draft`; no paid
generation, export, customer communication or publishing is authorized. The existing daily
owner briefing/audio surfaces can supply inputs, but they do not prove a public Margot video
pipeline or calendar sync.

**How that resolves inside Synthex.** `nexus-copywriter` is an estate-level Claude skill;
there is **no `nexus-copywriter` agent in this repo**. `.claude/skills/nexus-viral-run/SKILL.md`
already settled this: only the `senior-copywriter` skill exists, and the copy stage delegates
to a senior-copywriter-style producer over `getAIProvider()`, injected as `deps.generateCopy`.
Read every "delegates to `nexus-copywriter`" below as that binding. Naming a phantom agent is
what that resolution note exists to prevent.

## Node 0 — BRAND_CONTEXT (stored, not generated)

Written once per client, versioned, read by every downstream node. This is the grounding
record. It is not a prompt.

```
BRAND_CONTEXT {
  client:         string            // CARSI, NRPG, Disaster Recovery, RestoreAssist…
  offer:          string            // what is actually sold
  audience:       string            // who buys, in their own words
  audience_pain:  string[]          // problems they'd name unprompted
  proof:          string[]          // credentials, case outcomes, accreditations
  voice:          string            // register, forbidden phrasing, AU/UK spelling
  platforms:      string[]          // where this client actually posts
  constraints:    string[]          // regulatory, insurance, professional-body limits
}
```

_Note: `constraints` is not optional for the Unite-Group brands. Restoration and training
content sits close to insurance and accreditation claims. A pillar that implies a coverage
outcome or an accreditation the client does not hold is a liability, not a miss._

## Node 1 — Strategy

**reads:** `BRAND_CONTEXT`
**outputs:** `STRATEGY`

> Build a social strategy for the brand described in the attached context. Establish
> positioning against `{{COMPETITORS}}`, the specific audience segments worth addressing,
> what this brand can credibly say that others cannot, and the growth opportunities
> visible in that gap. Work only from the supplied context and the competitor material —
> do not assume industry facts not present in either.

```
STRATEGY {
  positioning:     string
  segments:        [{ name, motivation, objection }]
  differentiators: string[]     // each traceable to BRAND_CONTEXT.proof
  opportunities:   [{ description, rationale, platform }]
}
```

_The traceability rule on `differentiators` is what stops the model inventing strengths.
Anything not grounded in stated proof gets dropped at validation._

---

## Node 2 — Content pillars

**reads:** `STRATEGY`, `BRAND_CONTEXT`
**outputs:** `PILLARS`

> Define five content pillars for this brand. Each pillar must map to a stated audience
> segment and a stated differentiator. For each, give the pillar's promise to the reader,
> what it deliberately excludes, and eight post concepts spanning educate, demonstrate,
> and challenge.

```
PILLARS [{
  name:        string
  promise:     string
  excludes:    string          // what this pillar is NOT, to stop drift
  segment_ref: string
  concepts:    [{ concept, intent: educate|demonstrate|challenge }]
}]
```

_`excludes` is the field that keeps pillars distinct after fifty posts. Without it they
converge and you get five names for one pillar._

---

## Node 3 — Calendar

**reads:** `PILLARS`, `BRAND_CONTEXT.platforms`
**outputs:** `CALENDAR`

> Produce a 30-day calendar drawing on the supplied pillars. Distribute across pillars
> without repeating a concept. Assign each slot a format appropriate to its platform and
> a single objective. Cluster related posts so the month reads as a sequence rather than
> thirty unrelated items.

```
CALENDAR [{
  day:       1-30
  pillar_ref: string
  concept_ref: string
  platform:  string
  format:    carousel|reel|short|thread|single|story
  objective: visibility|engagement|lead|authority
}]
```

_One objective per slot. A post asked to do two things does neither, and the copy node
downstream has no way to resolve the conflict._

---

## Node 4 — Post copy _(fan out, one per slot)_

**reads:** one `CALENDAR` slot, its `PILLARS` entry, `BRAND_CONTEXT`
**outputs:** `POST`
**delegates:** hook and CTA to `nexus-copywriter` (in-repo: the `senior-copywriter` skill via
`getAIProvider()` / `deps.generateCopy` — see "How that resolves inside Synthex" above)

> Write the post for this slot. Open with a hook that earns the second line. Deliver the
> concept's value in plain language at the reading level of the stated audience. Close
> with a call to action matching the slot's objective — visibility asks for a share,
> engagement asks a question the reader has an answer to, lead asks for a next step.
> Respect the voice and constraints in the context.

```
POST {
  hook:      string
  body:      string
  cta:       string
  format_notes: string        // carousel slide breaks, thread splits
}
```

_This node and the original prompt 5 were the same job with a format parameter. Merged.
`format: reel|short` routes to the script shape below; everything else produces prose._

**Script variant** — when `format` is `reel` or `short`:

```
POST {
  hook:       string          // spoken, first 2 seconds
  beats:      [{ line, visual }]
  cta:        string
  runtime_s:  number
}
```

---

## Node 5 — Engagement layer

**reads:** `PILLARS`
**outputs:** `ENGAGEMENT`

> For each pillar, produce conversation starters, comment prompts, and community tactics
> that fit that pillar's promise. Prompts must be answerable by someone who has not read
> anything else from this brand.

```
ENGAGEMENT [{
  pillar_ref: string
  starters:   string[]
  prompts:    string[]
  tactics:    [{ tactic, cadence }]
}]
```

_The answerable-cold rule is the difference between a comment prompt and a question only
an existing follower can answer._

---

## Node 6 — Performance review ⚠ ANCHOR REQUIRED

**reads:** real platform analytics + published `POST` records
**outputs:** `REVIEW`
**status:** DO NOT SHIP until the analytics input is wired

> Analyse the attached performance data against the posts that produced it. Identify which
> pillars, formats, and objectives outperformed, and which underperformed. Attribute each
> conclusion to specific rows in the data. Where the data is insufficient to support a
> conclusion, say so rather than inferring.

```
REVIEW {
  findings:   [{ claim, evidence_rows: string[], confidence }]
  changes:    [{ change, rationale, expected_effect }]
  insufficient: string[]     // questions the data cannot answer
}
```

**This is the node that must not run on vibes.** Asked to "review my recent posts and
identify what works best" without attached metrics, the model will produce a fluent,
confident, entirely invented analysis — and it will be indistinguishable in tone from a
real one. That is the single highest-risk output in this pipeline, because it is the one a
client would act on.

`evidence_rows` is the anchor. Every finding must point at data the model did not author.
A finding with an empty `evidence_rows` is dropped, not softened.

Until platform analytics are connected, this node stays disabled. A missing performance
review is a visible gap; a fabricated one is not.

## The shape

```
BRAND_CONTEXT ──> STRATEGY ──> PILLARS ──┬──> CALENDAR ──> [fan out] POST × 30
                                          │
                                          └──> ENGAGEMENT

published POSTs + real analytics ──> REVIEW ──> (feeds next STRATEGY)
```

Node 3's fan-out is the only real parallelism — thirty posts have no dependency on each
other and should not run in a line. `ENGAGEMENT` and `CALENDAR` are independent of each
other and both read `PILLARS`, so they run at once.

The `REVIEW → STRATEGY` edge is what makes it a system rather than a one-shot. It is also
the edge that stays broken until node 6 has its anchor.

## Gaps in v0

1. **No analytics connector.** Node 6 is specified and disabled. This is the highest-value
   thing to build next — without it the loop does not close.

2. **No approval gate.** Verified in this repo at `main` (`4fec22aa2`):
   `lib/marketing-agency/full-campaign-generator.ts:644-649` emits

   ```ts
   approval: {
     status: 'approved',
     humanApproved: true,
     approvedBy: 'Codex execution agent',
     approvedAt: input.generatedAt,
   },
   ```

   `humanApproved` is a hardcoded literal and `approvedBy` names a machine as the human.
   The adjacent `evaluation` block (`:650-660`) is likewise nine hardcoded scores —
   `evidenceQuality: 86`, `accuracy: 86`, `approvalReadiness: 82` — none measured.

   This matters because the gate is real. `campaign-authority-manifest.ts` blocks in two
   places, and they are not the same condition:

   ```ts
   // :263-266 — per-claim, and only when the claim asks for it
   if (
     claim.humanApprovalRequired &&
     manifest.approval?.humanApproved !== true
   ) {
     blockers.push(`${claimId}_human_approval_required`);
   }

   // :302-305 — campaign-wide, unconditional
   if (
     manifest.approval?.status !== 'approved' ||
     manifest.approval.humanApproved !== true
   ) {
     blockers.push('campaign_human_approval_missing');
   }
   ```

   The generator does not bypass either gate; it hands both a pre-satisfied token.

   `authority-approval.ts:37` sets the same flag, but note the difference: that function
   (`approveCampaignAuthorityManifest`) takes `approvedBy` from its caller, so it is the
   shape a genuine approval action would use. The generator's is unconditional and names
   itself. Only the generator is the defect.

   Wiring this pipeline into autonomous runs before that is fixed would produce
   client-facing copy that self-certifies as reviewed. Treat it as a blocker, not a note.

3. **No claim validation against `constraints`.** A node that checks generated copy against
   the client's regulatory and accreditation limits before it reaches a human. For the
   restoration brands this should arrive before volume does.

4. **No per-platform voice variance.** One `voice` field currently serves every platform.
