## Decision up front

**Build the containment before the capability, and the measurement before the containment is loaded.** The fleet that builds Synthex gets less authority than the product it builds, because the repo already shows what happens when authored controls have no caller: the AI Governor `governedCall` is defined at [VERIFIED lib/ai/governor/index.ts:78] and has no production caller [VERIFIED command: git grep -l governedCall -- app lib lists only lib/ai/governor/index.ts, 2026-10-17], the immutable audit writer goes through the throwing stub [VERIFIED lib/security/audit-logger.ts:154-157] [VERIFIED lib/platform/server.ts:6-7], and 12 of 21 workflow files set `continue-on-error: true`, 8 of them on a whole job and the rest on single steps [VERIFIED command: grep -lE '^\s*continue-on-error:\s*true' .github/workflows/*.yml | wc -l gives 12 of 21 files, with job-level indent in 8 of them, 2026-10-17]. A plain `grep -l continue-on-error` gives 14 because two files only mention the string in a comment saying they do not use it [VERIFIED .github/workflows/ci.yml:161] [VERIFIED .github/workflows/repo-controls-drift.yml:91].

Decisions, each reversible only by editing a protected policy file under human review:

- **D1. Containment first.** Phase -1, the human bootstrap, installs the policy that the fleet cannot write. Phase 0 then ships before any other phase. The fleet runs on a host with an operating-system sandbox, never on native Windows, because Claude Code runs commands unsandboxed there and the sandbox covers shell commands only [VERIFIED https://code.claude.com/docs/en/sandboxing.md]. File tools, MCP servers and hooks run outside the sandbox, so path denial is a hook job, not a sandbox job.
- **D2. The repo agrees: PRs end at a human review and merge gate and production DDL is CEO-gated [VERIFIED .claude/skills/north-star/SKILL.md:61]. The fleet never merges, and its principal is never the approving account (Phase -1 item 4, and the human-merge step in the AI-only section).
- **D3. Zero new tables, zero new columns in fleet-built phases.** Storage is JSONL in the repo, the existing Redis idempotency store and existing audit and outcome models. New tables need CEO approval [VERIFIED roadmap.md:27].
- **D4. - **D5. Deterministic judges are final; JEV is advisory or disabled.** No LLM verdict can overturn a script verdict. JEV only triages failure clusters, and a day with no credential or $5 of metered spend means it is disabled and the run still completes.
- **D6. Role split against injection.** No agent holds both a channel for untrusted content and a capability to write, spend or publish. Readers read, builders build, releasers release, and each has a different tool list in a policy file.
- **D7. Order.** P-1 human bootstrap, P0 containment, P1 JEV deterministic core, P2 truth, P3 contract, P4 machine principal, P5 receipts and quotes, P6 outcomes, P7 delegated publish (built, never activated by the fleet), P8 content and image quality, P9 drills.

## Goals & non-goals

**Goals**

- G1. A fleet of Claude Code agents builds every phase with no human in the development loop, inside caps that hooks enforce.
- G2. A failed read never renders as a successful empty read, in the product or in the fleet's own reports. This is the no-fake-as-real rule applied to code.
- G3. Every one of the 764 routes is discoverable and typed, the publish, campaign and spend routes are retry-safe, and a scoped non-human principal can call them [VERIFIED command: find app/api -name route.ts | wc -l gives 764, 2026-10-17].
- G4. Every query in new or changed code carries `organizationId`, proven by a test that fails on a violation and by cross-tenant probes.
- G5. Calls, directions, bookings, rank and review signal for Australian local service businesses are measured and written with attribution.
- G6. Image and video generation stays grounded on the owned reference library, and the escape hatch becomes audited and approval-gated.
- G7. A release is a checkable object: tests, review and cost bound to one commit.

**Non-goals**

- NG1. No fleet merge, deploy, DDL apply, secret rotation, live-mode activation or branch-protection change.
- NG2. No Managed Agents for the development fleet. The service is in beta behind `managed-agents-2026-04-01`, is not eligible for zero data retention, and its `auto` permission policy is documented as not a human checkpoint [VERIFIED https://platform.claude.com/docs/en/managed-agents/permission-policies.md] [INFERENCE from tooling report S15].
- NG3. No Routines for write-capable work. Routine runs have no permission prompts and every included connector can write without asking [VERIFIED https://code.claude.com/docs/en/routines.md]. Routines are allowed only for read-only canaries with the minimum connectors.
- NG4. No Mythos 5.1 anywhere. It is limited to organisations verified through the Cyber Verification Program [INFERENCE from tooling report S20].
- NG5. No inbound voice agent, listings network, white-label portal or new messaging vendor in this programme. Competitors own those today and each needs a founder spend decision.
- NG6. No scraping of competitor products beyond public pages, public documentation and our own paid-account traffic under its terms. REA's own disclaimer sets the same line [VERIFIED https://raw.githubusercontent.com/morluto/rea/main/DISCLAIMER.md].
- NG7. No use of `useReferences: false` for any product, brand or client surface [VERIFIED .claude/rules/real-images-only.md:29-32].

## Approach

Plain language: **write the rules into files the fleet cannot edit, measure with scripts the fleet cannot soften, then let the fleet build inside both.**

The programme has three planes, and each guardrail lives in exactly one of them as a file, a hook or a test.

**Control plane (policy the fleet cannot write).** A pinned settings file kept outside the repository tree and passed with `--settings`, plus `--bare` so a hook or `.mcp.json` committed by a fleet PR does not execute in the next run. This matters because a `-p` run without `--bare` loads the project's hooks and `.mcp.json` even in a folder never trusted [VERIFIED https://code.claude.com/docs/en/headless.md direct fetch 2026-10-17]. The pinned directory is `$FLEET_HOME`, for example `~/.synthex-fleet/`, and holds the settings file, the MCP allow-list, the role file and the halt files. Two halt files exist, and they behave differently. A daily-ceiling halt is a date-stamped `STOP-<UTC date>` file that the wrapper writes and that stops applying at the next UTC midnight on its own, so a cost trip never needs a person and never breaks the 14-day soak. A security halt is the plain `STOP` file, written by the secret-scan hook, which only a person clears, and which counts as a human intervention in the phase receipt. Only a real hit writes it: the selftest drives the hook against a scratch halt directory (K3), so the cumulative gate in every phase leaves the real `STOP` absent and no phase is forced into a human intervention. The sandbox mounts `$FLEET_HOME` read-only for shell commands, so a builder's shell can read the halt files but cannot delete them. File tools run outside the sandbox [VERIFIED https://code.claude.com/docs/en/sandboxing.md], so the PreToolUse path hook, not the sandbox, denies Write and Edit calls on `$FLEET_HOME`. Run output lives in a second directory, `$FLEET_RUN`, which is writable by the wrapper process only, sits outside the repo tree and holds the ledgers, manifests and receipts; no agent role holds a write path to it. Inside the repo, a protected-path list names the files that define the containment layer: `.claude/settings*.json`, `.claude/hooks/**`, `.claude/done/**`, `.claude/rules/**`, `CLAUDE.md`, `.mcp.json`, `.github/**`, `scripts/fleet/**`, `scripts/release/**`, `scripts/gate/**`, `scripts/truth/**`, `scripts/api/exempt-routes.json`, `scripts/check-repo-controls.mjs`, `release-receipts/**`, `tests/eval/jev/floors.json`, `vercel.json`, `prisma/migrations/**`. A PreToolUse hook denies every fleet write to them except one: the Releaser's receipt write goes through `scripts/release/verify-receipt.mjs --write`, which is itself protected. A CI job fails any pull request that touches a protected path without a human-applied label, with one exemption: a pull request whose only protected-path change is its own phase's `release-receipts/P<n>.json` passes the label job when `verify-receipt.mjs` validates that receipt and exits 0. The receipt is therefore checked by a protected script and needs no extra human label, so a phase pull request can go green before a person acts. PreToolUse can return allow, deny, ask or defer and can rewrite tool input [VERIFIED https://code.claude.com/docs/en/hooks.md direct fetch 2026-10-17]. `.claude/done/**` is a local layer on the fleet host, so the CI job cannot police it; the sandbox mount and the hook do, and everything CI must see is mirrored into the tracked paths above.

**Work plane (the fleet).** A workflow script fans work out as one subagent per unit, each in its own worktree. The workflow runtime caps concurrency at 16 agents by default and 1,000 agents per run, accepts no mid-run user input, and needs a `Workflow` allow rule under `-p` [VERIFIED https://code.claude.com/docs/en/workflows.md]. Worktree isolation blocks edits and git redirects that target the main checkout but does not track what a shell `cp` or redirect writes, so the sandbox and the path hook carry that case [VERIFIED https://code.claude.com/docs/en/worktrees.md direct fetch 2026-10-17]. The headless documentation says `--bare` exposes the shell, file read and file edit tools and skips subagent auto-discovery [VERIFIED https://code.claude.com/docs/en/headless.md direct fetch 2026-10-17]. It does not say that the `Workflow` tool is present under `--bare`, that `agent()` calls inside a workflow bind to the `--agents` role definitions, or that the per-role tool lists hold for workflow-spawned agents [UNCONFIRMED U11]. The P0 selftest probes all three. If any probe fails, the orchestrator is a plain Node script that starts one `claude -p --bare --agents` process per unit, which keeps the same roles and tool lists and needs no workflow runtime.

**Evidence plane (what proves it).** The evidence is the Done contract with its locked verifier scripts [VERIFIED .claude/done/work/w_700ccb6f54bf/contract.json:18-28], the JEV case files and floors, and the release receipt. The repo's own rule is that a subagent's "build passes" report stays unconfirmed until the orchestrator re-runs the gauntlet on the integrated tree [VERIFIED .claude/rules/fabel-evidence-standard.md:20-24]. This spec adds a design decision of its own on top of that rule: the re-run is made by a Verifier role in a fresh context, so no builder grades itself [INFERENCE from D6 and the role table, a choice of this spec and not a requirement of the cited file]. The contract and its verifiers sit under `.claude/done/` on the fleet host, a local layer, and the tracked mirror that CI can read is `release-receipts/`.

**Rule 5: four states, never three.** Every harness result, every receipt and every fleet step ends in PASS, FAIL, INCONCLUSIVE or DISABLED. INCONCLUSIVE means the check could not run. It never counts as a pass and never blocks a merge by itself. DISABLED means a lane or credential was missing and the run finished without it. This is the no-fake-as-real rule written as an enumeration, and `scripts/fleet/attest-phase.mjs` rejects any receipt that carries a fifth value.

### Bootstrap order and the write carve-out

The protected list contradicts the plan unless the order is stated, so here it is. The containment cannot install itself, and a fleet that may not write the containment files cannot build them either. Four rules close that circle.

- **Rule B1: Phase -1 front-loads every protected file.** A Claude Code session with the founder present builds all of them in one supervised pull request: the guard hook in two placements (rule B4), the pinned settings, five CI jobs under `.github/workflows/` named `protected-paths` (the label job), `jev-ratchet` (fails any diff that lowers a floor or deletes a case without a tombstone entry), `openapi-drift` (fails when a route has no spec entry), `receipt-verify` (runs `verify-receipt.mjs`) and `jev-pr` (the per-pull-request script cases), `scripts/fleet/**` (the wrapper and phase orchestrator `run-phase.mjs`, the Node fan-out fallback `fanout.mjs`, selftest, verify-protected, provision, gen-contracts, check-bootstrap, check-ledgers, check-governor-mode, next-row, attest-phase, apply-proposals, drill, check-soak), `scripts/release/**` (verify-receipt, verify-waterline), `scripts/gate/check-held.mjs`, `scripts/truth/check-noop.mjs`, `scripts/jev/check-ratchet.mjs` and a zero-valued bootstrap `tests/eval/jev/floors.json`. The wrapper, the orchestrator and the fan-out fallback are listed because they live under the protected `scripts/fleet/**` path that the fleet may not write, so unless a person writes them here no phase can start. `scripts/check-repo-controls.mjs` already exists [VERIFIED scripts/check-repo-controls.mjs] and joins the protected list without being rebuilt. `gen-contracts.mjs` then derives the ten phase contracts from the Phased plan table below and locks them with `donectl`, so no phase ever writes its own contract. Every human act in this phase is a row in the Phase -1 table below. `check-bootstrap.mjs` verifies each row mechanically and the Phase -1 receipt counts each one as a human act, so nothing in P0 to P9 depends on an act that is not listed there. It also verifies that each of the five CI job names is defined under `.github/workflows/` and appears as a check run on the Phase -1 head commit. The five jobs are advisory checks that the human merger reads; making one a required status check changes branch protection and is a founder decision outside this programme.
- **Rule B2: two later protected changes travel as proposals, and a person lands them after the phase merges.** The first measured `floors.json` (P1) and any growth of the exempt-route list (P3) are written by the fleet into `proposals/<phase>/<path>`, a tracked and unprotected staging directory inside the phase pull request. Phase -1 ships a zero-valued bootstrap `floors.json` and an empty exempt list, so both protected files exist and the checks have something to read. A phase's checks read the proposal where it sits, so a verifier can run them on the fleet head with no human act: `node scripts/jev/check-ratchet.mjs --base origin/main --proposal proposals/P1/tests/eval/jev/floors.json` and `node scripts/api/gen-openapi.mjs --check --exempt proposals/P3/scripts/api/exempt-routes.json`. The phase branch holds no human-authored commit, so `attest-phase.mjs` sees an AI-only diff and `verify-receipt.mjs` sees a head bound to the reviewed commit. After the merge, a person runs `node scripts/fleet/apply-proposals.mjs`, which opens one separate, human-authored branch that moves the proposed files into place and deletes the staging directory. That follow-up is a waterline act recorded in the waterline ledger. It belongs to no phase, and later phases overlay a present proposal over the in-place file when they run their checks, so none of them waits for it. The `check-held.mjs` update that P7 once needed is not a proposal: Phase -1 ships `check-held.mjs` able to assert the held-by-default rule for both shapes of the code, the current `HOLD_FOR_REVIEW` constant and the P7 function `resolveHoldState`, and `gen-contracts.mjs` fixes that function name in the P7 contract. P7 therefore changes no protected script.
- **Rule B3: writers other than agents are not agents.** The Releaser writes `release-receipts/P<n>.json` through `scripts/release/verify-receipt.mjs --write`, a protected script. The Verifier returns its receipt as JSON and the wrapper process writes it to `$FLEET_RUN/receipts/`, a writable directory outside the read-only policy directory, because a read-only `$FLEET_HOME` would block that write. A receipt cannot name its own commit, so it names the reviewed commit and the tested tree, and the check passes only if the diff from that commit to the head is the receipt file alone.
- **Rule B4: two guard placements ship, and the selftest picks the one that works.** Placement A is a PreToolUse hook registered in the pinned settings file. Placement B is a settings file with deny rules only, covering the protected paths, the forbidden commands and the denied MCP tool classes, plus a wrapper post-run check that reads the run's stream-json tool log and the worktree diff and discards a unit whose log or diff shows a protected path or forbidden command. Placement B detects after the fact what placement A prevents, so it is the weaker of the two, and the manifest records which one a run used. `selftest.mjs` fires the planted attempts under each placement and selects A if the hook denies them, otherwise B if the deny rules do. If neither placement denies them, `check-bootstrap.mjs` fails item 2 in Phase -1 with the founder present, so P0 never starts on an unproven guard.
- **Rule B5: a host scheduler entry starts each phase, so no person starts one.** The Scheduler (see the roles table) has three entries on the fleet host. The nightly and weekly entries start the wrapper. The phase-advance entry runs every 30 minutes and does one job. It fetches `origin/main`, finds the lowest phase P<n> whose `release-receipts/P<n>.json` is absent, and starts `node scripts/fleet/run-phase.mjs --phase P<n>` only when four conditions hold: the previous phase's receipt is on `origin/main` and `node scripts/release/verify-receipt.mjs` exits 0 for it (for P0, `node scripts/fleet/check-bootstrap.mjs` exits 0 on `origin/main` instead), no branch matching `feature/fleet-p<n>-*` exists on the remote, no run lock for P<n> exists in `$FLEET_RUN`, and P<n> is not on hold. A phase that ends FAIL or INCONCLUSIVE gets a hold row in the ledger and is retried at most once per UTC day, inside the daily cost ceiling. The entry never edits a file and never answers a prompt, and it starts at most one phase at a time, which keeps the repo's one-pull-request-at-a-time rule. Every start is a row in the run ledger, and `check-soak.mjs` fails when a merged receipt has no start row within 24 hours. A person installs the three entries once, as Phase -1 item 10, and the Phase -1 receipt counts that as a human act.

Fleet runs can trust none of this until the selftest has fired each denial from a planted attempt on the real host, which is the first job of Phase 0.

The Scheduler is not a Routine. Routines run in Anthropic's cloud and cannot start a process on a WSL2 or Mac Mini fleet host, and their connectors write without asking [VERIFIED https://code.claude.com/docs/en/routines.md]. The nightly, weekly and phase-advance wrapper runs (rule B5) are started by the host's own scheduler (cron on WSL2, launchd on the Mac Mini), or by a Desktop scheduled task, which runs locally with a one-minute minimum interval and has no seven-day expiry [INFERENCE from tooling report S26, which gives the seven-day expiry for session scheduling and local execution for Desktop tasks]. That is what drives the 14-day soak, because `/loop` session tasks expire after 7 days [INFERENCE from tooling report S26]. The Scheduler holds no tool that can write and opens no issue. A failed run shows in the ledger and in the `check-soak.mjs` exit code. An alert channel would be a new connector and so a founder decision, and this programme builds none. No phase depends on a Routine. ### Three tests and one rule

Every element of the plan passes three tests or is cut. **Metric:** which of the client metrics O1 to O7 below does it move, and in which direction. **Gap:** which competitor capability in the SWOT does it close. **Number:** which command prints the figure that proves it. **Rule: no actuator without a meter.** Publishing, review requests and content generation are actuators. Each ships only after the metric it is meant to move can be read, for a synthetic organisation in the fleet's tests and for the pilot organisation in production.

## JEV test harness

The JEV harness is how the fleet finds, tracks and closes the gaps in the SWOT without a human reading results. It is a library of bounded cases that scripts run and judge, with a model used only where a script cannot decide. JEV, the TypeSafe advisory decision provider, is one optional step at the end: it triages clusters of failures. It never decides whether a case passes. If it is unavailable for any reason, the harness reports it as DISABLED and the run still completes.

**Bounds, as hard limits.** Every case is a bounded decision contract: a fixed input shape, a fixed output shape declared as a Zod schema and emitted as JSON Schema with the existing helper [VERIFIED lib/ai/structured-output.ts:10], one model turn, no tools, and a timeout. A judge or triage prompt carries at most 32k input tokens inside a 64k context window. A case that does not fit is split by its generator or recorded INCONCLUSIVE. Nothing is silently truncated. Token counting uses the free count endpoint before a batch is built [VERIFIED https://platform.claude.com/docs/en/build-with-claude/token-counting.md]. Output schemas avoid recursion, external references and numeric or string length bounds, which constrained decoding does not support, so length limits are checked by the validator after decoding [VERIFIED https://platform.claude.com/docs/en/build-with-claude/structured-outputs.md].

**Size.** The target is 2,630 cases across 12 families, a number in the thousands that fits the daily ceiling below [INFERENCE from the case-family plan in the research input `jev-spec.json`]. Of these, 1,830 are judged by a script alone and cost nothing in model spend. The other 800 get a script pre-check and then a model pair.

**Positive controls, so a green cannot be fake.** Each family ships at least three planted-failure cases, for example a route that deliberately returns 200 without auth in a test fixture. The runner refuses to record a family as green unless its planted failures went red in the same run. This is the rule that a null result is not evidence until the check has been shown able to return non-null. A family whose controls stay green is recorded BROKEN_CHECK and fails the run.

**Judge routing.**

1. A script verdict is final. No model can overturn a red from a script.
2. Browser-only properties use the existing Playwright setup [VERIFIED package.json:262].
3. A model judges only what a script cannot check: whether a claim's source entails it, whether copy is on brief, whether an image matches its references. Two judges score each item, a disagreement goes to a third, and at least one judge must sit outside the generator's family. The first family is a non-Anthropic lane, the second is `claude-sonnet-5-5`, and `claude-opus-5-5` breaks ties [INFERENCE from the global release-law text and the research input `jev-spec.json`]. The release-law script `independent_review.py` reviews pull request diffs and is not a per-item judging interface, so the per-item call goes through the same lane's single-prompt command. For the lane in use on 17 October 2026 that is the Mac Mini command `mm-ask`, and its key lives on that machine only [INFERENCE from the founder directive supplied with this task and the auto-memory note on the MiniMax review lane]. Whether the fleet host can reach it, and whether it accepts one item per call, is [UNCONFIRMED U3]. If the generator was an Anthropic model, an all-Anthropic pair is not allowed, so those cases end INCONCLUSIVE whenever the non-Anthropic lane is unreachable.
4. `claude-haiku-5-5` screens input for injected instructions and does vision checks. Anthropic's own guidance is to screen tool output with a small classifier model and to state in the system prompt that tool content is data [VERIFIED https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks.md].
5. JEV triage runs last and is advisory only.
6. **Exit behaviour of the judged run.** `npm run jev:judged` exits 0 only when both families judged every case in scope and the calibration bars below are met. It exits 3, INCONCLUSIVE, when the non-Anthropic lane failed its start probe, and it exits 1 on any hard-gate red. An exit of 3 never counts as a pass. Judged verdicts from a single family are marked UNCALIBRATED and count for nothing, so Phase 8 cannot silently become single-judge and cannot stay red for good. The deterministic half of Phase 8 must still exit 0, and finish-line item 2 depends on the deterministic hard gates alone, so a down lane delays the judged floors and stalls nothing else.

**Cross-model judging, and why.** A language model scores its own output higher than a rival's, and the effect grows with how well it recognises its own text [VERIFIED https://arxiv.org/abs/2404.13076 direct fetch 2026-10-17]. That fetch, made in this session and logged in the research input record, shows the paper by Panickssery, Bowman and Feng, "LLM Evaluators Recognize and Favor Their Own Generations", v1 dated 15 April 2024. The page names no peer-reviewed venue, so the spec treats it as a preprint and designs the controls to hold even if the effect is smaller than reported. The controls are structural:

- The judge family must differ from the generator family, read from the run manifest. An unknown generator id means script judging only and every model-judged case is INCONCLUSIVE.
- The generator identity is removed from the judged text, item order is randomised, pairs are scored in both positions, temperature is fixed and scores are length-normalised.
- A judge counts only after calibration: it must catch at least 90 percent of planted-defect mutants and fail at most 10 percent of known-good items. Agreement between the two judges must reach a kappa of 0.6. Below either bar the verdict is UNCALIBRATED and counts for nothing.
- Twenty of the J11 cases plant instruction text inside the content under judgement. A judge that obeys it is disqualified until recalibrated. Content under judgement is passed as JSON-encoded data, never as instructions [INFERENCE from the injection guidance in tooling report S17].

The runner aborts a batch submission when the ledger plus the batch's estimate would pass $4.75. The estimate uses assumed token sizes [UNCONFIRMED U2], so the first run re-measures them with the free count endpoint and rewrites this table.

**JEV advisory contract.** JEV receives a summary of one failure cluster: family, gap id, route, counts, fingerprint. It never receives credentials, client data, personal data or production responses, because every case runs against synthetic organisations. - No credential is present. On 17 October 2026 no credential for the decision provider was found in the stores searched, and the seven-store sweep timed out [UNCONFIRMED U1]. The harness therefore starts DISABLED.
- The daily ledger is at or above $4.75.
- The model lane failed its start-of-run probe.
- The summary exceeds 32k input tokens or carries a field flagged sensitive.

A CI check fails any diff that lowers a floor or deletes a case without a tombstone entry. Floors start at the first measured values and only rise. A known-gap case that flips to pass needs a linked evidence path.

**Feedback loop.** A script groups red cases by fingerprint and writes one row per group into `BACKLOG.md` between marker comments: gap id, first seen, count, evidence path, owner. A row is never closed silently. It closes only when its cases are green on two consecutive runs and a golden J12 case exists. The backlog already carries dead gate checks that this loop must not hide [VERIFIED BACKLOG.md:11-13].

**What can still go wrong.** Day-one noise will be high, because many cases start red against the 88 stub-dependent files. Floors start low by measurement. Synthetic tenants limit realism, and no staging environment is confirmed as a target [UNCONFIRMED U7]. There is no human label set, so calibration rests on planted defects and may miss Australian trade nuance. A founder spot-check of 20 judged items a quarter is optional and listed as a question (Q5).

## AI-only operation (no human in the loop)

**Claim.** Development of every phase runs with no human in the loop: no person reviews a diff, answers a permission prompt, edits a file or restarts an agent between phase start and the opening of the pull request. Humans appear only at the waterline, plus the one stated exception of Phase -1 below. This is not a claim that nobody is accountable. The founder owns every waterline gate, and a phase receipt records the count of human interventions, which must be zero for the phase to be called AI-only.

**Why prompts are not the control.** Anthropic reports that users approved about 93 percent of permission prompts, so human approval is one layer and not the main control [VERIFIED https://www.anthropic.com/engineering/how-we-contain-claude]. The same source says tool output is an attack surface even when the tool is trusted and that containment starts at the environment layer. The operating model follows that order: environment first, then policy hooks, then model instructions last.

**The release path, with the merge gate intact.**

1. The fleet works in isolated worktrees and integrates into one phase branch. The repo's rule is one pull request at a time and no stacked unmerged work [VERIFIED .claude/skills/north-star/SKILL.md:64]. A phase is therefore one branch and one pull request, and the next phase starts from the merged result, started by the phase-advance entry (rule B5).
2. The orchestrator re-runs the full gate on the integrated tree. Subagent reports stay unconfirmed until it does [VERIFIED .claude/rules/fabel-evidence-standard.md:20-24].
3. The Releaser role runs the independent-review script bound to the exact head commit and lets it exhaust every lane. A single vendor being down is not evidence that review is unavailable. Only an exit with a named reason per lane means unavailable, and then the work is queued, not self-certified [INFERENCE from the global release-law text supplied with this task].
4. GitHub runs CI on the exact head, which is the push-run of the `feature/fleet-p<n>-<slug>` branch (D9). A pull request opens only after that run is green.
5. A human merges. The standing autonomous-merge exception in the global law names three other repositories and not Synthex, so it does not apply here [INFERENCE from the global CLAUDE.md]. No push restriction limits who may merge, because `restrictions` is null [VERIFIED command: gh api repos/CleanExpo/Synthex/branches/main/protection --jq .restrictions gives null, 2026-10-17]. ### The loop

Each unit of work follows the same eight steps, and each step ends in a command and an exit code that the orchestrator writes to the ledger.

1. `node scripts/fleet/next-row.mjs` picks one row from the marker block in `BACKLOG.md` and prints a contract: input files, the single branch name, the proving command. It exits 0 with a contract, and exits 3 when the backlog is empty, which is a stop condition.
2. Build in a fresh worktree off `origin/main` on `feature/fleet-p<n>-<slug>`, after the wrapper has provisioned it. One coherent branch per scope. A second pull request for the same scope is a release-law failure and the wrapper refuses it.
3. Run `npm run type-check && npm run lint && npm test`, exit 0 [VERIFIED .claude/rules/development/workflow.md:55].
4. Run the Done preflight: `donectl status` and `donectl selftest`. A missing, stale or failing gate means enforcement is unproven and nothing may be called done [INFERENCE from the global done-gate rule].
5. Run `python3 ~/.claude/skills/pr-release-gate/scripts/independent_review.py --brief <brief> --base <sha> --head <sha> --repo <worktree> --out <report.json>` and let it exhaust every lane. Only exit 2 with a named reason per lane means unavailable, and then the work is queued, never self-certified [INFERENCE from the global CLAUDE.md release law].
6. Push the one branch only after the review report names the exact head. GitHub then runs that head. The wrapper proceeds only when `gh run list --branch <branch> --json headSha,conclusion` shows the same head with conclusion success.
7. Open the pull request once, with the report path, the head SHA and the receipt path in its body. This is the fleet's last act on the phase.
8. A human merges. `node scripts/release/verify-waterline.mjs` then reads the actor of each waterline event and exits non-zero if any actor is a fleet principal.

**Activation is not a phase.** Merging, enabling a live platform connection, recording an autonomy policy and flipping `HOLD_FOR_REVIEW` are human acts that follow the phase receipt. A phase never claims them.

## REA and Nate B. Jones: how the method was applied

The method in one line, taken from both sources: study the shipped artefact and the evidence, not the marketing. REA supplies the technique and Nate B. Jones supplies the discipline about what counts as done.

### REA lessons

REA is an MIT-licensed MCP server, command line and agent skill that lets a coding agent inspect shipped software, such as native binaries, Electron apps, APKs and websites, on the local machine and return findings with evidence and limitations [VERIFIED https://github.com/morluto/rea]. It is not affiliated with REA Group. This section takes its method and leaves the tool uninstalled.

**What the published investigations show.** The Aegis authenticator study found the code-generation function among 3,077 classes, rebuilt it, and matched 133 cases and the RFC test vectors [VERIFIED https://rea.tools/showcase/aegis/]. The Notion study traced one clipboard write from the preload script to Electron's clipboard API and found the hidden block identifier in the copied HTML [VERIFIED https://rea.tools/showcase/notion/]. Both start narrow, trace callers, read the code and then check a rebuilt version against the original. A QuickBooks community study, not written by REA staff, states "not full parity" and lists what it could not do [VERIFIED https://github.com/morluto/rea/discussions/2198]. That honesty about scope is the part worth copying.

**Lessons the spec applies.**

- **A1. Evidence, limitations, unknowns on every result.** REA returns an evidence record with a graph and a list of unknowns, never a bare answer [INFERENCE from the research input `rea.method`]. Synthex's receipts (P5) and honest-status contract (P2) copy the shape: a failed read says what it could not read.
- **A2. One contract, three surfaces.** Typed MCP tools, a `--json` command line and an installable skill share one contract [INFERENCE from the research input `rea.how_it_integrates`]. P3 publishes the contract once and the MCP server card is generated from it.
- **A3. A read-only `doctor` before any setup.** P5's ops read tools play this role, so an agent can find that a connector is declared and not wired before it plans work on it.
- **A4. Behaviour fixtures from public artefacts.** Record how a platform or competitor behaves from public pages, public documentation, published APIs and our own paid-account traffic under its terms, and keep each observation as a testable fixture. Do not clone [INFERENCE from the research input `rea.lessons_for_synthex`].
- **A5. Clean-room split.** One agent writes a behaviour specification, and a different context builds from it. The Reader and Builder roles already enforce this split.

**Limits.** REA's own disclaimer allows research on software you own or are authorised to examine, and it refuses to help bypass licence checks, copy proprietary code or tamper with online services [VERIFIED https://raw.githubusercontent.com/morluto/rea/main/DISCLAIMER.md]. For a competitor's hosted product, REA only sees the client side. Synthex stays on public pages and its own account traffic, and does not bypass logins or rate limits.

**Why it is not installed in the fleet.** `npx rea-agents setup` writes an MCP registration and a skill into the agent's configuration with backups [VERIFIED https://github.com/morluto/rea]. Agent configuration is a protected path, and installing third-party code with local analysis privileges is a new dependency under D4. If the founder wants it, it is installed by a human on a research host and its output enters the fleet as Reader-class evidence, which is data and never instruction. The Windows route needs a current Node version and a full JDK for native analysis, and the research stage could not confirm the install on the founder's machine [INFERENCE from the research input `rea.windows_setup_notes`].

### Nate B. Jones lessons

Nate B. Jones writes and speaks on AI strategy, and his video on REA argues that a vibe-coded app can look right and fall apart after launch [VERIFIED https://www.youtube.com/watch?v=PseF3LyXQ04]. His working rule for this spec is to study the shipped artefact and the evidence, not the marketing. A competitor claim becomes VERIFIED only when a page was opened or a file was read, and otherwise stays a lead (U5). A completion message from an agent is a claim until a check ran. A demo that looks finished is not a result. The companion paid post was not opened, and the principles below come from the free pages the research stage read.
